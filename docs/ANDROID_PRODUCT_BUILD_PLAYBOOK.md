# Android product build playbook

> **Current multi-device overlay — 2026-09-24:** Panther is a frozen reference and K1/K2 is merged. The Panther/GrapheneOS observations later in this document are historical target-specific learning, not the active universal deployment model. New devices use explicit artifact kinds and adapter-owned transport/partition semantics.


Status: **normative build-orchestration and evidence guidance; product semantics remain owned by the appropriate Sable repositories.**

This document captures reusable lessons from Android product-build work so Panther and future device targets do not rediscover target-selection, generated-product, product-composition, storage, and failure-preservation behavior through repeated long builds.

It describes **how to build and prove a product**. It does not decide which applications, roles, permissions, overlays, or device semantics SableOS should ship.

## 1. Ownership model

Keep these boundaries explicit:

```text
platform_manifest
    exact source composition and revisions

vendor_sable
    common Sable product/package composition

device_sable_<target>
    bounded device-specific Sable integration

upstream / generated vendor product
    substrate and hardware input

build
    orchestration, preflight, execution, validation and evidence
```

Do not patch common Sable package choices into an adevtool-generated Google product, generated vendor tree, or unrelated upstream device product merely because that is where `PRODUCT_PACKAGES` is currently visible.

Generated substrate files are inputs to reproduce and validate. Sable-owned semantics belong in Sable-owned source.

## 2. Resolve the target before building

A long Android build must not be the mechanism used to discover the target configuration.

For Android 17-era trees, treat lunch identity as a product/release/variant selection. Record the exact successful invocation, for example:

```text
lunch <product>-<release>-<variant>
```

Do not assume the historical two-part form `<product>-<variant>` is valid.

Before build execution, prove at least:

```text
TARGET_PRODUCT=<expected product>
TARGET_BUILD_VARIANT=<expected variant>
EXPECTED_BUILD_ID=<substrate/device expected value>
RESOLVED_BUILD_ID=<actual build value>
```

Also record the release configuration supplied to `lunch`. Do not depend solely on `get_build_var TARGET_RELEASE`: some Android 17 configurations may accept a release-qualified lunch invocation while that variable is empty.

The exact lunch invocation plus the resolved release-dependent configuration and Build ID are the evidence.

## 3. Product-specific Build ID handling

Android build make resolves a product-specific Build ID first when the tree provides one, conceptually:

```make
BUILD_ID := $(BUILD_ID_$(TARGET_PRODUCT))
```

A substrate may populate values such as:

```text
BUILD_ID_panther=...
```

through `cmds-for-envsetup.sh` or equivalent environment setup.

Rules:

- source the normal tree environment setup before target resolution;
- record the product-specific Build ID source;
- verify the final resolved Build ID before build execution;
- do not set a manual shell `BUILD_ID` override merely to bypass a device/product guard;
- do not assume a derived Sable product automatically inherits `BUILD_ID_<base-product>` just because its makefile inherits the base product;
- before introducing a derived product name, explicitly design and prove its release/Build-ID mapping.

A Build-ID guard failure is target-configuration evidence. It is not a reason to weaken the guard.

## 4. Diagnostic commands are not all equivalent

Some helper commands perform partial or pre-product configuration and may fail differently from a fully qualified `lunch` path.

For example, a release-listing helper can encounter a generic/fallback Build ID before target-specific product configuration and trigger a generated device guard. Treat this as a diagnostic-path limitation until proven otherwise; do not automatically conclude that the requested release is invalid.

When helper output conflicts with a proven target setup:

1. preserve the helper failure;
2. inspect where target-specific environment variables are loaded;
3. run the exact intended lunch configuration read-only;
4. verify product, variant, Build ID, and relevant release-dependent inputs;
5. only then classify target viability.

## 5. Generated product ownership

Before modifying product composition, determine whether the active product files are generated.

Common indicators include headers such as:

```text
Generated by <tool>; do not edit
```

and a generator-owned skeleton/specification tree.

For generated substrate products:

```text
GENERATED_PRODUCT_MUTATION_ALLOWED=NO
```

unless a separately reviewed architecture explicitly says otherwise.

A generated product may contain hundreds of normal `PRODUCT_PACKAGES` entries. That does not make it the correct location for Sable package selection.

## 6. Product-composition proof ladder

A module can be completely valid while still being absent from the finished OS image. Always distinguish these layers:

```text
1. source/module definition exists
2. build system discovers the module
3. module compiles successfully
4. install rules are generated
5. selected product includes the module
6. expected artifact exists in PRODUCT_OUT
7. artifact is represented in installed-file inventories
8. artifact is incorporated into the appropriate image
9. package/component exists at runtime
10. user-visible behavior passes
```

Do not infer layer 5 from layers 1-4.

Useful evidence has different meanings:

- `all_modules.txt`: module discovery, not product selection;
- `module-info.json`: module metadata and possible install destinations, not proof the product selected it;
- `installs-<product>.mk`: install rules exist, not proof those outputs were requested by the product;
- `installed-files*.txt`: product-installed-file evidence;
- actual `target/product/<product>/...` paths: PRODUCT_OUT artifact evidence;
- image inspection/runtime package state: image/runtime evidence.

A successful full Android build can therefore coexist with a Sable product-composition failure. Report both claims separately.

## 7. Preflight for a full product build

Before starting a long build, record a preflight that includes:

```text
authorization flags
workspace/root identity
source revisions and clean/dirty state
manifest/source-composition identity
vendor/generator revision and generated-input identity
target product/release/variant invocation
expected and resolved Build ID
OUT_DIR identity and allowed mutation scope
existing build-process check
required input presence
network/fetch policy
initial free space
storage abort/floor policy
```

If the requested target cannot be resolved exactly, stop before compilation.

If the workspace contains generated inputs that fail their own version/Build-ID guards, stop and classify the mismatch rather than overriding it.

## 8. Long-running build execution

Long product builds should run under a persistent session such as `tmux` or an equivalent managed process wrapper.

The build wrapper should:

- print the authorization boundary before execution;
- use the already validated target configuration;
- preserve stdout/stderr in a durable log independent of the terminal session;
- launch the build so loss of the interactive terminal does not automatically terminate it;
- record the child build PID/process group where practical;
- monitor storage periodically;
- preserve partial output on failure;
- record build return code and elapsed time;
- record source/worktree poststate.

If the `tmux` session disappears, do **not** automatically restart the build. First inspect:

```text
active soong/ninja/siso processes
persistent console log
build/evidence log
result markers
PRODUCT_OUT/image inventory
storage state
```

Only rerun under a new authorization after classifying the previous attempt.

## 9. Storage policy

AOSP/Android full builds can consume substantially more storage than early Soong analysis suggests.

Use both:

```text
START_FREE_SPACE_FLOOR
RUNTIME_FREE_SPACE_MONITOR
```

A build wrapper should periodically record free space and OUT size. If an authorized abort floor is crossed, stop in a way that preserves evidence and partial output rather than deleting the tree.

Do not assume a floor that was barely sufficient once is a generally safe capacity recommendation. Record actual peak/output growth and revise device/host profiles with margin.

## 10. Failure preservation and diagnosis

When a build or later closure check fails:

```text
DO_NOT_CLEAN_AUTOMATICALLY
DO_NOT_CLOBBER_AUTOMATICALLY
DO_NOT_DELETE_OUT_AUTOMATICALLY
DO_NOT_RERUN_AUTOMATICALLY
```

First classify the failure:

```text
TARGET_CONFIGURATION
SOURCE_INPUT
COMPILE
PRODUCT_SELECTION
PRODUCT_INSTALL
IMAGE_COMPOSITION
ARTIFACT_VALIDATION
RUNTIME
HOST_ENVIRONMENT
STORAGE
```

Preserve logs, partial outputs, source poststate, and generated configuration evidence.

A closure script must not label the whole build `FAIL` merely because a later product-artifact expectation failed after Ninja itself completed successfully. Prefer separate markers such as:

```text
FULL_ANDROID_BUILD=PASS
REQUIRED_IMAGES=PASS
REQUIRED_SABLE_PRODUCT_ARTIFACT=FAIL
FULL_SABLE_PRODUCT_CLOSURE=FAIL
```

## 11. Incremental continuation

After a successful long build exposes a bounded composition/configuration defect, an incremental continuation may be appropriate when:

- the existing OUT is preserved and understood;
- no clean/clobber is required by the change;
- the source/configuration mutation is separately authorized;
- the changed inputs are intentionally consumed by the Android build system;
- storage remains sufficient;
- the evidence explicitly labels the result as incremental continuation.

Incremental success does not replace a later clean reconstruction proof when milestone/release policy requires one.

## 12. Panther / GrapheneOS Android 17 reference learning

The following observations came from the Panther R6 build investigation and are reference evidence, not universal constants for every future substrate release.

Observed target/substrate:

```text
GrapheneOS release: 2026091000
Device: panther / Pixel 7
Successful lunch invocation: panther-cur-user
Expected/resolved Build ID: CP2A.260705.006
Generated product: vendor/google_devices/panther/panther.mk
Vendor generator: GrapheneOS adevtool
```

Key findings:

- `panther-user` was rejected because the tree required product/release/variant lunch syntax;
- the generated Panther environment exported `BUILD_ID_panther=CP2A.260705.006`;
- the generated Panther product rejected the generic older Build ID;
- a `list_releases panther` diagnostic failed during pre-product configuration with the generic Build ID, while the fully qualified `lunch panther-cur-user` path resolved the correct Panther Build ID;
- `get_build_var TARGET_RELEASE` was observed empty after the successful lunch path, so it is not sufficient as the sole release-selection proof;
- the full Panther build completed successfully and emitted the required image set;
- SableStart was known to Soong, had generated install rules, and had module metadata, but was not selected into the product and therefore did not appear in PRODUCT_OUT/installed-file inventories;
- the active Panther product file was adevtool-generated and was therefore rejected as the location for Sable common package integration;
- the incident demonstrated why compile proof, install-rule proof, product-selection proof, and runtime proof must be separate gates.

These observations should inform future Panther profile updates, but every new GrapheneOS/vendor release must re-resolve its own Build ID, generated inputs, target syntax, and image expectations.

## 13. Future-device profile checklist

For every new device/substrate combination, answer before the first full build:

```text
What exact upstream/substrate revision is being built?
What exact product/release/variant invocation is valid?
Where does the device-specific Build ID come from?
What exact Build ID is expected?
Which device/vendor files are generated and therefore non-owning?
Which Sable repository owns common product inclusion?
Which Sable repository owns target-specific adaptation?
Which repositories/revisions compose the intended tree?
What required images define basic build closure?
What Sable packages define product closure?
What is the storage start floor and abort policy?
What network access is authorized during acquisition and build?
What OUT/evidence directories may be mutated?
What failure state must be preserved?
```

Do not begin a multi-hour product build until these questions are either answered or explicitly recorded as the bounded purpose of the build.

## 14. Anti-patterns

Avoid:

- old two-part lunch assumptions on a tree requiring release-qualified selection;
- manual Build-ID overrides to make a generated product guard pass;
- editing generated vendor/device products for common Sable semantics;
- treating `all_modules.txt` as proof of product inclusion;
- treating install rules as proof an APK is in the image;
- treating a successful full Android build as complete Sable product closure;
- deleting a valuable OUT after a late closure failure;
- clean/clobber as a reflexive retry mechanism;
- starting another long build before checking free-space margin;
- embedding one device's absolute workspace path or Build ID into generic orchestration;
- allowing build tooling to invent product ownership or application policy.

The desired pattern is: **resolve target, bind inputs, build once, preserve evidence, classify exactly, and repair at the owning architectural layer.**
